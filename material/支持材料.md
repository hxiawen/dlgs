# 支持材料

[返回索引](../MVP_index.md) | [任务说明](../readme.md)

## 该项在 MVP 上架中的作用

支持材料回答用户两个问题：

- 出问题了去哪找人
- 这个产品背后是不是真的有人维护

这对公开上架尤其关键，因为商店评论区不是正常客服系统。

## 当前判断 / 当前缺口

当前仓库没有看到成熟的：

- Homepage URL
- Support URL
- FAQ / help 页面
- 面向用户的支持邮箱或工单入口

这意味着：即使扩展上架，用户遇到问题后也没有清晰路径。

## 需要做的事情

最小支持包建议包含：

- 一个对外主页或说明页
- 一个支持入口
- 一个联系邮箱或表单
- 一页常见问题

对 `Dualogues` 第一版更具体一点：

- 支持邮箱：优先产品域名邮箱；三天内来不及时，至少用一个产品专用 Gmail
- 支持页：可以先把“主页 + 支持 + FAQ”合成一个最小静态页

## 注意事项

- 不要用无人维护的链接凑数。
- 不要把关键支持入口绑在个人临时邮箱上。
- 支持材料要与商店页、隐私政策、产品内入口一致。

## 指南 / 标准 / 要求

第一版支持策略建议：

- Chrome Web Store Support hub：开启
- 外部 Support URL：也准备一个
- 联系邮箱：使用稳定的产品邮箱别名

第一版支持邮箱的最低标准：

- 不是个人主邮箱
- 能长期收信
- 能转发
- 有人值守

第一版支持页的最低标准：

- 解释这个扩展是干什么的
- 明确当前只支持什么范围
- 放常见问题
- 放联系方法
- 放数据删除说明

这样做的好处是：

- 商店内有原生支持入口
- 商店外也有可控支持页面
- 将来迁移客服工具时成本更低

## 操作步骤

1. 决定支持模式：
   - 只用商店 Support hub
   - 商店 Support hub + 外部支持页
2. 准备支持内容：
   - 产品简介
   - 常见问题
   - 反馈方式
   - 数据清理说明
3. 先把支持邮箱建好，再验证确实能收到测试邮件。
4. 开启通知，验证确实能收到。
5. 写 3 到 5 条标准回复模板：
   - 安装后没反应
   - 看不到 Widget
   - 跳转不准
   - 想删除数据
6. 在商店后台填写 Homepage URL / Support URL。

## 验收标准

- 用户不需要进评论区也能找到支持入口。
- 团队有人负责看通知并回复。
- 支持入口、隐私政策、产品边界说明互相一致。
